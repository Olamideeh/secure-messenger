# MESSAGE_ARCHITECTURE.md

## 1. Purpose

Define the architecture for end-to-end encrypted messaging in Secure Messenger.

The system must support:
- One-to-one messaging.
- Multiple devices per account.
- Offline message delivery.
- Reliable retries without duplicate messages.
- Delivery and read receipts.
- Message history and pagination.
- Real-time communication through WebSocket.
- Future Android and iOS clients.

The backend must never receive plaintext messages or users' private encryption keys.

## 2. Architecture decisions

| Area | Decision |
|---|---|
| Initial conversations | Direct conversations |
| Message identity | Server UUID + client-generated UUID |
| Sender identity | Authenticated user and registered device |
| Encryption | Client-side E2EE |
| Server storage | Ciphertext envelopes and delivery metadata |
| Database | PostgreSQL |
| Message submission | REST API |
| Real-time delivery | WebSocket over TLS |
| Message history | REST API with cursor pagination |
| Duplicate prevention | Unique sender-device/client-message ID |
| Delivery receipts | Per recipient device |
| Read receipts | Per recipient device |
| Offline delivery | Persisted encrypted envelopes |
| Retry behavior | Idempotent |
| Ordering | Server timestamp plus message UUID |

## 3. Message lifecycle

1. Sender writes a message on their device.
2. The client encryption layer encrypts the message using the selected E2EE protocol.
3. The client creates a unique client message UUID.
4. The client prepares the encrypted envelope or envelopes required by recipient devices.
5. The client submits the message to the backend.
6. The backend authenticates the user and validates the sender device.
7. The backend verifies active conversation membership.
8. The backend checks for a duplicate request.
9. The backend persists the message and its encrypted envelopes in one transaction.
10. The backend returns an accepted response.
11. The backend notifies recipient devices over WebSocket when available.
12. Offline recipients retrieve pending envelopes after reconnecting.
13. Recipient devices acknowledge delivery.
14. Recipient devices acknowledge read status when appropriate.

A successful database transaction means the server accepted the message. It does not mean the recipient received or read it.

## 4. Message identity and duplicate prevention

Every message has two identifiers:

- `id`: UUID generated by the backend.
- `client_message_id`: UUID generated by the sending client before the first submission.

The unique idempotency key is:

`(sender_device_id, client_message_id)`

If a client retries because the network failed, the backend must return the existing message result instead of inserting another message.

The client must reuse the original `client_message_id` when retrying. It must not generate a new one for the same logical message.

## 5. Message ownership and authorization

Every message belongs to exactly one conversation and has exactly one sending user and sending device.

The backend must verify:

- The authenticated session belongs to the sending user.
- The sending device belongs to that user.
- The device is active and has not been revoked.
- The user is an active member of the conversation.
- The recipient devices are eligible members' active devices.

Never trust a sender user ID supplied by the frontend as proof of identity.

Conversation membership must be checked for both message submission and history retrieval.

Removing a contact must not automatically delete existing conversations or messages.

## 6. Encrypted payload design

The backend stores encrypted envelopes, not plaintext messages.

A logical message may have multiple envelopes because different recipient devices can require different encrypted payloads.

The application-level envelope record contains:

- Message association.
- Recipient device association.
- Ciphertext bytes.
- Protocol/envelope version.
- Server-generated creation timestamp.

The actual cryptographic envelope structure, headers, and cryptographic metadata must be defined by the selected E2EE protocol.

We must not invent our own encryption algorithms, key exchange, ratchet, nonce handling, or cryptographic serialization.

The backend must not store:

- Plaintext message content.
- Private identity keys.
- Private prekeys.
- Decrypted message previews.
- Plaintext search indexes.
- Plaintext message content in application logs.

## 7. Database design

### Table A: `messages`

One row represents one logical message.

| Column | Purpose |
|---|---|
| id | UUID primary key |
| conversation_id | Conversation foreign key |
| sender_user_id | Sending user foreign key |
| sender_device_id | Sending device foreign key |
| client_message_id | Client-generated UUID |
| created_at | Database-generated timestamp |

Constraints:

- Primary key on `id`.
- Foreign key to conversations.
- Foreign key to users.
- Foreign key to registered devices.
- Unique constraint on `(sender_device_id, client_message_id)`.

Index:

`(conversation_id, created_at DESC, id DESC)`

### Table B: `message_envelopes`

Stores the encrypted payloads for individual target devices.

| Column | Purpose |
|---|---|
| id | UUID primary key |
| message_id | Message foreign key |
| recipient_device_id | Target device foreign key |
| protocol_version | Version of the envelope format |
| ciphertext | Encrypted payload as binary data |
| created_at | Database-generated timestamp |

Constraints:

- Primary key on `id`.
- Foreign key to messages.
- Foreign key to registered devices.
- Unique constraint on `(message_id, recipient_device_id)`.
- Ciphertext must not be null or empty.
- Enforce a maximum ciphertext size.

### Table C: `message_receipts`

Tracks delivery and read acknowledgements per recipient device.

| Column | Purpose |
|---|---|
| id | UUID primary key |
| message_id | Message foreign key |
| recipient_device_id | Recipient device foreign key |
| delivered_at | Nullable delivery timestamp |
| read_at | Nullable read timestamp |

Constraints:

- Primary key on `id`.
- Foreign key to messages.
- Foreign key to registered devices.
- Unique constraint on `(message_id, recipient_device_id)`.
- `read_at` cannot be earlier than `delivered_at` when both exist.

An acknowledgement must be idempotent. Repeated delivery or read acknowledgements must not create additional receipt records or move an existing timestamp backwards.

### Important database decision

We will not add one general `status` column to `messages`.

A single status cannot correctly represent delivery to multiple recipient devices.

Instead:
- Server acceptance is represented by successful persistence and the submission response.
- Delivery is represented by `delivered_at` in the relevant receipt.
- Read is represented by `read_at` in the relevant receipt.

## 8. Message ordering and pagination

Use cursor-based pagination instead of relying on large offset queries.

Messages are ordered by:

`created_at DESC, id DESC`

The UUID is the tie-breaker when multiple messages have the same timestamp.

The client receives a cursor representing the last message in the page and uses it to retrieve older messages.

The backend must:
- Verify active conversation membership.
- Apply the cursor consistently.
- Return messages in deterministic order.
- Avoid returning messages belonging to conversations the user cannot access.

The first request retrieves the newest messages. Subsequent requests retrieve older messages.

## 9. REST API design

Base path: `/api/conversations`

### Submit a message

`POST /api/conversations/{conversationId}/messages`

The request contains:
- Client message UUID.
- Sender device UUID.
- Encrypted envelope data for eligible target devices.

The authenticated session supplies the sender identity.

Successful first submission returns HTTP 201.

A recognized retry returns the existing result without creating another message.

### Retrieve messages

`GET /api/conversations/{conversationId}/messages?cursor={cursor}&size={size}`

Returns encrypted message envelopes and pagination information.

### Acknowledge delivery

`POST /api/messages/{messageId}/receipts/delivered`

The authenticated recipient device acknowledges receipt.

### Acknowledge read

`POST /api/messages/{messageId}/receipts/read`

The authenticated recipient device acknowledges that the message has been read.

### Retrieve pending messages

`GET /api/messages/pending`

Returns encrypted envelopes intended for the authenticated user's eligible devices that have not yet been acknowledged as delivered.

## 10. WebSocket architecture

WebSocket provides real-time delivery notifications and encrypted envelope delivery.

It must use the existing authenticated HTTP session.

Security requirements:
- TLS in production.
- Validate the authenticated session during connection.
- Validate device ownership.
- Restrict subscriptions to authorized users/devices.
- Do not trust client-provided user IDs for subscriptions.
- Do not put session credentials in URL query parameters.
- Apply message size limits and connection limits.

REST and WebSocket must use the same message service and authorization rules.

WebSocket delivery is not the permanent source of truth. PostgreSQL remains the source of truth for persisted messages and receipts.

## 11. Offline delivery and reconnection

A recipient may be offline when a message arrives.

The server keeps the encrypted envelope in PostgreSQL.

When the recipient reconnects:
1. The client authenticates.
2. The client retrieves pending encrypted envelopes.
3. The client processes and decrypts them locally.
4. The client acknowledges successful delivery.
5. The client acknowledges read status when appropriate.

WebSocket notifications can be retried or missed. The REST pending-message endpoint provides recovery.

The client must deduplicate messages using the server message UUID.

## 12. E2EE protocol selection gate

The protocol selection from Phase 4 is provisional.

Before production encryption is implemented, validate:

- Maintained implementation and security support.
- Browser/TypeScript support.
- Future Android and iOS compatibility.
- Device registration and multi-device support.
- Asynchronous messaging.
- Key rotation and recovery.
- Forward secrecy and post-compromise security.
- License and distribution constraints.
- Compatibility with our custom Spring Boot backend.

We will not implement cryptographic primitives ourselves.

The backend message schema will remain independent of protocol-specific ciphertext details through a versioned envelope boundary.

## 13. Reliability and security requirements

- Persist messages and their envelopes transactionally.
- Enforce idempotency with database uniqueness.
- Verify sender device ownership.
- Verify active conversation membership.
- Verify recipient device eligibility.
- Enforce payload size limits.
- Rate-limit message submission and receipt acknowledgements.
- Do not log plaintext or encryption keys.
- Avoid logging complete ciphertext payloads.
- Use database constraints as the final defense against duplicate records.
- Keep message history available after temporary disconnection.
- Do not treat WebSocket delivery as proof of successful receipt.

## 15. Definition of done

The messaging phase is complete when:

- Users can exchange encrypted messages.
- The server never receives plaintext message content.
- Messages are persisted reliably.
- Duplicate retries do not create duplicate messages.
- Only authorized conversation members can access messages.
- Multiple devices can receive their intended encrypted envelopes.
- Delivery and read receipts work per recipient device.
- Message history supports pagination.
- Offline recipients can recover missed messages.
- WebSocket reconnection works.
- Security and integration tests pass.
